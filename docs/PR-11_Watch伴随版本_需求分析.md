# PR-11 Apple Watch 伴随版本需求分析

| 版本 | 日期 | 依赖 |
|---|---|---|
| v1.0 | 2026-05-29 | PR-01~PR-10（Core MVP + 模板与动作库 CRUD + 训练日历安排 + 首页重设计完成） |

---

## 1. 目标

### 1.1 解决的问题

力量训练中有三个高频的「手机交互障碍」场景：

1. **组间休息**：组间低头解锁手机查看倒计时，打断注意力；休息计时的通知出现在屏幕顶部，转瞬即逝，错过后需要重新操作
2. **记录一组**：卧推、深蹲等大重量动作完成后，手机往往在离身处（旁边的凳子、腰包）；站起来找手机、解锁、定位到当前动作，这段操作流程打断了训练节奏
3. **手机不在身边**：部分用户将手机锁入储物柜，整个训练过程中与手机物理隔离

Apple Watch 贴在手腕上，与手机的互补关系正好覆盖以上三个场景。

### 1.2 目标场景

- 训练中，用户不拿起手机，在手腕上完成「记录这一组」的操作（重量、次数、RPE、左/右侧）
- 组间休息时，Watch 显示倒计时，到时震动提醒，用户一眼确认该继续了
- 手机放在包里或旁边未激活状态时，Watch 上的计时和记录操作不受影响

### 1.3 核心价值

**训练中手不离铁，Watch 在腕，数据不漏。**

## 2. 设计原则

1. **Watch 是伴随设备，不是独立 App**：iPhone 是训练数据的唯一权威来源，第一版 Watch 不承担完整训练管理职责；Watch 的价值在健身房环境下的交互便利，而非功能完整性
2. **每一步操作控制在 5 秒以内**：Watch 屏幕小、出汗影响触摸精度；与其追求全功能覆盖，不如把核心流程做到极致流畅
3. **通信中断不能丢失已完成的动作**：iPhone 和 Watch 之间的连接随时可能短暂断开；凡是用户在 Watch 上已确认的记录，不能因通信抖动而丢失
4. **Watch UI 独立重新设计，不搬运 iPhone 界面**：iPhone 和 Watch 的交互方式根本不同，Watch 界面不是 iPhone 页面的等比缩小

## 3. 范围

### 3.1 本次做

| 功能 | 说明 |
|---|---|
| 当前训练状态展示 | 显示进行中的训练名称、动作列表、每个动作已完成组数 |
| 快速记录一组 | 在 Watch 上输入重量、次数、可选 RPE 和左/右侧；数据传回 iPhone 落库 |
| 参考上组数据 | 进入动作时，展示该动作上一组的重量和次数，供用户参考 |
| 休息计时器 | 完成一组后自动启动倒计时；支持跳过、延长 30 秒；到时震动提醒 |

### 3.2 本次不做

| 项 | 说明 |
|---|---|
| Watch 独立开始/结束训练 | 第一版由 iPhone 发起训练，Watch 加入已有 session |
| 模板与动作库管理 | 不在 Watch 上做配置类操作 |
| 训练历史浏览 | 不在 Watch 上查看历史记录或统计 |
| CSV 导出 | 不适合 Watch 场景 |
| HealthKit Workout 集成 | 有价值，涉及额外权限和 Workout session 生命周期，留给后续版本 |
| 表盘 Complication / Smart Stack | 可作为后续增强；不作为第一版核心功能 |
| Watch 离线独立训练 | 手机完全不在范围内时独立完成完整训练，复杂度高，留给后续版本 |
| 在 Watch 上修改或删除已记录的组 | 第一版只支持新增，修正操作在 iPhone 上完成 |

### 3.3 连接中断范围（v1）

| 级别 | 描述 | v1 承诺 |
|---|---|---|
| 短暂不可达 | 手机在包里、锁屏或离身数步，通常数分钟内自动恢复 | Watch 计时和记录正常运行；已确认记录进入本地队列，恢复连接后同步至 iPhone |
| 整场断开 | 手机锁入储物柜，整场训练期间无法通信 | Watch 计时和记录正常运行；已确认记录持久化至本地队列，训练后连接 iPhone 时批量同步 |

以上两种场景均以「iPhone 已开始训练，且训练快照至少已同步一次至 Watch」为前提；Watch 在本地快照范围内继续运行，不支持独立开始或结束训练。

**「同步完成」的定义**（验收触发口径）：本文档不承诺后台机会式传输的时限，只承诺最终一致。一条待同步记录视为「同步完成」当且仅当 iPhone 明确确认其已落库。涉及时限的验收（如 8.1「恢复连接后出现 N 条」）一律以**双方前台可达后达到的最终态**为判定基准，不以某次后台传输是否即时送达为准。

**数据不丢契约**：用户在 Watch 上已确认的记录，在目标 session 仍存在的前提下，无论中断时长，最终在 iPhone 落库后有且仅出现一次。

**记录终态**：每条 Watch 记录在以下终态之一收敛，并对应明确的 Watch 展示——

| 终态 | 含义 | Watch 展示 |
|---|---|---|
| 待同步 | 已在 Watch 确认，尚未收到 iPhone 落库确认 | 「待同步」 |
| 已同步 | iPhone 已确认落库 | 「已同步」 |
| 需用户处理 | 目标 session/动作已不存在（离线期间 iPhone 已结束并归档、删除 session、或动作被移除），落库不可能完成 | 提示用户该记录无法自动归位，需在 iPhone 上处理 |

「需用户处理」态下记录不丢弃、不静默吞掉；iPhone 侧如何呈现与消化这些记录的细节留待 7（开放问题）。重试时机与「待同步」转「需用户处理」的判定时机同样见 7。

### 3.4 Watch 缺失时的降级行为

Watch 伴随功能是对 iPhone 主流程的纯增强。无已配对 Watch、Watch app 未安装或从未打开时，iPhone 端所有训练功能保持完整可用，不展示错误或降级提示。

## 4. 设备角色与数据流

**iPhone**：训练数据的唯一权威来源。负责存储所有训练记录，是 Watch 所需训练信息的来源，也是 Watch 发出的记录事件的最终落库方。

**Watch**：训练中的交互遥控器。只在训练进行中提供价值，不持久存储完整业务数据；但可为已确认记录保留待同步事件队列，直到 iPhone 明确确认落库。Watch 需要能在 iPhone 临时不可达时（用户离手机几步远、手机锁屏后短暂延迟）继续独立运行休息计时器。

**数据流向（需求层面描述，不锁定通信方案）**：

| 方向 | 内容 |
|---|---|
| iPhone → Watch | 当前训练快照（见下方契约） |
| Watch → iPhone | 用户完成一组的记录事件（见下方契约） |

**业务数据契约**：以下是各方向必须承载的业务信息，描述「需要哪些信息」而非通信格式或字段命名，供工程在技术方案中具体化。

*当前训练快照（iPhone → Watch）至少包含：*

| 信息 | 用途 | 缺失后果 |
|---|---|---|
| session 标识 | 记录事件回指、去重、确认归属 | 离线记录无法定位到正确训练 |
| 动作稳定身份 | 区分同名动作、记录事件定位 | 同名动作记录串位 |
| 动作展示名 | Watch 列表展示 | 无法显示动作 |
| 单/双侧属性 | 决定是否出现侧别选择步骤（5.2） | 侧别流程无依据 |
| 默认休息时间 | 自动启动休息计时（5.3） | 计时器无法自动起算 |
| 单位（kg/lb） | 重量输入与展示（5.2） | 单位歧义 |
| 各动作已完成组数 | 列表展示、侧别推断（5.2） | 进度与推断失准 |
| 上组参考数据 | 进入动作时展示（5.4），需覆盖「当前 session 最近一组」与「历史最近一组」两种来源 | 5.4 兜底无数据 |

*记录事件（Watch → iPhone）至少包含：*

| 信息 | 用途 |
|---|---|
| 目标 session 标识 | 落库归属，校验 session 是否仍存在 |
| 目标动作稳定身份 | 落库定位，校验动作是否仍存在 |
| 重量、次数 | 记录主体 |
| RPE（可选）、侧别（单侧动作） | 记录补充 |
| 完成时间 | 排序与展示 |
| 去重标识 | 保证「有且仅出现一次」（见 3.3 契约），重试不产生重复 |

## 5. 功能需求

### 5.1 当前训练状态展示

| 状态 | Watch 展示 | 是否可记录 |
|---|---|---|
| 无进行中的训练 | 显示等待状态，提示在 iPhone 上开始训练后才可使用 | 否 |
| iPhone 已开始训练但快照未达 Watch | 显示「等待训练数据」，不展示动作列表 | 否（快照到达前禁止记录） |
| 有进行中的训练（快照已同步） | 显示训练模板名称 + 动作列表（每个动作标注已完成组数） | 是 |
| 训练结束 | Watch 退出训练中状态，返回等待页 | 否 |

「快照未达」是 3.3 离线能力的承重前提：Watch 必须先收到当前训练快照才进入可记录态；在此之前即便用户已在 iPhone 上开始训练，Watch 也只显示等待、不允许记录。

iPhone 端训练状态发生变化（开始/结束）后，Watch 应在第 6 节规定的同步延迟内更新。

### 5.2 快速记录一组

用户在 Watch 上完成单次记录的交互流程：

1. 从动作列表选择当前动作
2. 输入重量（数字；单位跟随 iPhone 的 kg/lb 设置）
3. 输入次数（正整数）
4. 可选：输入 RPE（6 / 7 / 8 / 9 / 10）
5. 若为单侧动作：选择左侧或右侧（双侧动作此步骤跳过）
6. 确认提交

记录确认后：
- Watch 给出即时视觉或触觉反馈；iPhone 当前可达时展示「已同步」，不可达时展示「待同步」（将在恢复连接后自动提交）
- 自动进入休息计时器
- 当前动作的已完成组数在本地立即更新，不等待 iPhone 确认

**单侧动作的侧别推断**：若该动作在当前 session 内左/右侧组数不平衡，Watch 应推断并预选组数较少的一侧，用户可覆盖。

**重量和次数的输入方式**：应采用选择器或拨盘风格的控件（而非文字键盘），以适应出汗、单手操作、手套等健身房实际环境。

### 5.3 休息计时器

| 行为 | 说明 |
|---|---|
| 自动启动 | 完成一组记录后，以该动作的默认休息时间启动倒计时 |
| 倒计时显示 | 突出显示剩余时间（秒数） |
| 震动提醒 | 倒计时归零时 Watch 震动，提醒用户可以开始下一组 |
| 跳过 | 用户可提前结束计时，返回动作列表或记录界面 |
| 延长 30 秒 | 计时中或归零后可追加 30 秒 |
| 手机不可达时 | 休息计时器在 Watch 本地独立运行，不依赖与 iPhone 的实时连接 |
| Watch 腕向下后恢复 | 重新抬腕时，剩余时间应基于实际流逝时间正确显示，不出现「时间冻结」 |
| 归零时腕向下 | 若倒计时归零时 Watch 腕向下，用户抬腕后应补发震动提醒并展示已归零状态，不静默跳过 |

> **注**：watchOS 不保证后台计时器进程在腕向下期间持续运行。计时逻辑应以「目标结束时刻」为锚点，而非依赖持续递减的计数进程。「归零时腕向下，抬腕后补发震动」依赖系统级提醒能力：补发触觉依赖通知权限，若权限未授予则降级为界面展示已归零状态而不补发震动（具体技术选型见第 7 节）。

### 5.4 参考上组数据

进入某个动作的记录界面时，展示该动作最近一组的重量和次数：

- 优先展示当前 session 内该动作的最近一组
- 若当前 session 尚未记录该动作，展示历史任意 session 的最近一组
- 此数据仅供参考展示，不强制预填输入框；用户需主动确认或修改后才能提交

## 6. 体验约束

以下约束来自 Watch 硬件特性和健身房使用环境，工程与设计侧需在此范围内寻找方案：

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 单次记录操作完成时间 ≤ 5 秒 | 出汗影响触摸精度；组间注意力有限 | 输入方式必须支持选择器/拨盘，不应依赖软键盘 |
| 腕向下后计时仍需准确 | watchOS 不保证后台计时进程 | 计时逻辑以目标结束时刻为基准 |
| 记录流程步骤数应尽量少 | Watch 屏幕小，多层级导航体验差 | 在功能和流程层级之间做取舍 |
| 单侧动作的侧别选择应支持单手触摸 | 训练时另一只手可能持铁 | 选择控件触摸面积需足够大 |
| 震动提醒需能被手腕感知 | 健身房噪音环境；用户注意力不在手腕 | 使用具有存在感的触觉类型，不使用弱震动 |
| 训练状态同步延迟（iPhone reachable 时） | Watch 展示准确性依赖及时更新 | 训练开始/结束变更后 Watch 更新 ≤ 5 秒；完成一组后 Watch 侧组数更新 ≤ 3 秒 |

## 7. 开放问题

以下问题需要在工程或产品层面进一步决策，本文档不锁定答案：

| 问题 | 背景 |
|---|---|
| 重量单位的同步实现方式（工程待决策） | v1 单位跟随 iPhone 设置已确认（见 5.2）；待决策：训练中用户在 iPhone 修改单位时，Watch 是实时更新，还是以训练快照中的单位为准直至下次同步 |
| 记录发送失败时的重试与终态判定时机 | 终态枚举已在 3.3 锁定（待同步 / 已同步 / 需用户处理）；待决策：重试节奏，以及 iPhone 长时间无法确认时 Watch 何时将「待同步」转为「需用户处理」 |
| 「需用户处理」记录在 iPhone 侧的呈现与消化 | 终态已锁定（3.3）；待决策：目标 session/动作已不存在的离线记录，iPhone 端以何种 UI 让用户重新归位或丢弃 |
| 后台计时的技术选型 | 需求已锁定「以目标结束时刻为锚点 + 权限允许时补发震动」（5.3）；待决策：在本地通知方案与 extended runtime session 方案之间确认实现（两者各有权限和后台资源限制） |
| Watch 端的错误反馈粒度 | RPE 不合法、动作不存在等校验失败时，Watch 应以何种形式告知用户（考虑 Watch 小屏的展示能力）？ |

## 8. 验收标准

### 8.0 验收前置条件

| 条件 | 要求 |
|---|---|
| 最低系统版本 | iOS 17 或以上；watchOS 10 或以上 |
| 验收设备 | 真实 iPhone + 已配对的 Apple Watch（模拟器无法验证 WCSession 通信和触觉反馈） |
| 权限 | （8.1 功能验收前提）Watch 通知权限已授权；触觉反馈未关闭（设置 → 声音与触感）。通知权限未授权的降级路径由 8.2 单独验收 |
| 5 秒同步 SLA 适用前提 | Watch app 已安装、已打开至前台，且 iPhone 与 Watch 当前可达；Watch app 未打开或不可达时此 SLA 不适用 |

### 8.1 功能验收

- 当 iPhone 上有进行中的训练时，Watch 应在 5 秒内显示该训练的动作列表及各动作已完成组数（iPhone reachable，见第 6 节同步延迟约束）
- 当 iPhone 上无进行中的训练时，Watch 应显示等待状态，不展示空训练列表
- 当用户在 Watch 上完成一组记录操作并确认后，该组数据应在 iPhone 的当前训练页正确出现
- 当用户在 Watch 上完成记录后，Watch 侧对应动作的已完成组数显示应随之更新
- 当用户完成一组记录后，休息计时器应自动以该动作的默认休息时间启动倒计时
- 当倒计时归零时，Watch 应震动提醒用户
- 当用户点击「跳过」时，计时器停止，Watch 返回动作列表或记录界面
- 当用户点击「+30 秒」时，剩余时间应增加 30 秒
- 当 Watch 腕向下后重新抬起时，剩余倒计时时间应与实际流逝时间一致，不出现时间冻结
- 当倒计时归零时 Watch 腕向下，用户抬腕后 Watch 应补发震动提醒并展示已归零状态，不静默跳过
- 当 iPhone 与 Watch 通信中断时（含短暂不可达和整场断开，见 3.3），Watch 上正在进行的倒计时不应受影响
- 当 Watch 与 iPhone 断开连接期间在 Watch 上完成 2 组记录，双方前台可达恢复后达到最终态时（见 3.3「同步完成」定义），iPhone 当前训练页应出现恰好 2 条新记录，无重复、无遗漏
- 当同一组记录因通信失败触发重试，最终落库后 iPhone 端不应出现重复条目
- 当 iPhone 已开始训练但训练快照尚未同步至 Watch 时，Watch 应显示「等待训练数据」且不允许进入记录流程（见 5.1）
- 当动作为单侧动作时，记录流程应出现左/右侧选择步骤；双侧动作不出现此步骤
- 当在当前 session 内已有该动作记录时，进入记录界面应展示该 session 内最近一组的重量和次数
- 当在当前 session 内无该动作记录时，应展示历史最近一组的重量和次数
- 当 iPhone 结束训练后，Watch 侧应退出训练中状态并显示等待页
- 当 Watch 上存在单侧动作且当前 session 左/右侧组数不平衡时，进入记录界面应预选组数较少的一侧

### 8.2 发布降级 gate

以下用于发布判断，证明 Watch 伴随功能为纯增强、不影响存量 iPhone 用户：

- 当设备无已配对 Watch、或 Watch app 未安装/从未打开时，iPhone 端所有训练功能（开始/记录/结束/历史）行为不变，不展示错误或降级提示（见 3.4）
- 当 Watch 通知权限未授权时，Watch 仍可正常记录并显示休息计时，但不承诺归零震动；归零时应展示明确的「已归零」降级状态而非静默（见 5.3）。此情形按降级通过判定，不计为失败
